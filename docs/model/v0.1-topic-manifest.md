| 项目 | 值 |
| --- | --- |
| 模型标识 | `TOPIC-MANIFEST-MODEL-V0.1` |
| Schema 版本 | `0.1.0` |
| 状态 | 已接受 |
| 接受日期 | 2026-09-07 |
| 适用范围 | EMI Knowledge 多专题索引与组合发布 |
| 设计决定 | [Decision 0002](../decisions/0002-dora-topic-index-and-release-composition.md) |

## 1. 职责

专题清单为一组核心知识对象提供稳定入口。它记录专题范围、来源复核、建设状态、入口 Requirement、补充上下文和待确认问题，并供校验与发布工具选择对象。

法规事实和实施规则继续由六类核心知识对象承载。多个专题可以引用同一对象，仓库中只保留一份对象内容。

## 2. 字段

| 字段 | 内容 | 规则 |
| --- | --- | --- |
| `id` | 全局稳定的专题标识 | 使用小写英文、数字和连字符；以 `<domain>-` 开头 |
| `schema_version` | 专题清单 Schema 版本 | 当前固定为 `0.1.0` |
| `revision` | 同一专题清单的修订号 | 从 `1` 开始递增 |
| `title` | 专题标题 | 结构化正文使用 English |
| `language` | 工作语言 | 当前固定为 `en` |
| `domain` | 法规或知识领域 | 当前首个领域为 `dora` |
| `lifecycle_status` | 生命周期状态 | `draft`、`in_review`、`approved`、`superseded` 或 `retired` |
| `source_review_ids` | 采用的来源复核记录 | 至少一项，保存稳定复核标识 |
| `scope` | 摘要、包含项和排除项 | 三部分均必须明确，包含项和排除项不得为空 |
| `entry_requirement_ids` | 专题入口 Requirement | 草稿可以为空；批准状态至少一项 |
| `context_object_ids` | 需要额外带入的知识对象 | 可以引用六类对象，不得与入口 Requirement 重复 |
| `coverage` | 六类知识对象的建设状态 | 使用 `not_started`、`in_progress` 或 `complete` |
| `open_questions` | 专题级待确认问题 | 可以为空；发布时原样保留 |

清单路径固定为：

```text
knowledge/topics/<domain>/<id 去掉 domain 前缀>.yaml
```

例如 `dora-ict-change-management` 保存为 `knowledge/topics/dora/ict-change-management.yaml`。

## 3. 批准条件

专题进入 `approved` 前需要满足：

1. 至少有一项入口 Requirement。
2. `Source`、`Provision`、`Requirement`、`Decision`、`Control` 和 `Verification` 六项覆盖状态均为 `complete`。
3. 所有入口和上下文引用均能解析到已批准知识对象。
4. 解析结果中的所有对象均为 `approved`，不存在断裂引用，并通过完整知识图检查。

专题可以在批准时保留明确的 `open_questions`。这些问题随 Topic 一起进入发布制品，使用方仍需按权限处理具体机构判断。

## 4. 对象解析

发布工具按以下顺序求出专题对象闭包：

1. 从 `entry_requirement_ids` 和 `context_object_ids` 开始。
2. 沿对象的正向运行依赖收集 Provision、Source、Decision 依据及其他被引用对象。
3. 为已选 Requirement 收集关联 Control 和相关 Decision。
4. 为已选 Control 收集 Verification 和相关 Decision。
5. 重复解析，直到没有新对象加入。
6. 按对象类型和稳定 ID 排序，生成确定性输出。

解析器不会从共享 Source 反向收集仓库内所有 Provision，因此一个专题不会因引用 DORA 主法规自动包含其他 DORA 专题。

`replaces` 记录历史替代关系，不作为运行依赖扩展。被替代对象可以留在仓库或历史发布中，新发布继续保留其稳定 ID，同时无需把 `superseded` 对象加入当前 Topic 闭包。

## 5. 发布配置

新发布通过 `topic_selection` 显式选择专题：

```json
{
  "topic_selection": {
    "directory": "knowledge/topics",
    "schema": {
      "id": "TOPIC-MANIFEST-SCHEMA-V0.1",
      "version": "0.1.0",
      "path": "schemas/v0.1/topic-manifest.schema.json"
    },
    "topic_ids": [
      "dora-ict-change-management"
    ]
  }
}
```

使用专题选择的新发布采用 [`v0.2 release artifact Schema`](../../schemas/v0.2/release-artifact.schema.json)。生成结果包含：

- `knowledge.json` 和 `agent-context.json` 中的完整 Topic 清单及对象闭包。
- `manifest.json` 中的 Topic ID、修订、状态、文件路径和 SHA-256。
- Topic Schema、知识 Schema、来源基线和其他发布输入的 SHA-256。
- 同时覆盖 Topic 与知识对象内容的发布摘要。

## 6. 兼容边界

`v0.1.0` 的发布配置没有 `topic_selection`，继续使用 `schemas/v0.1/release-artifact.schema.json` 和全目录对象。生成器保留这条旧路径，自动化测试逐字比较固定制品，防止专题功能改变既有发布。

## 7. 检查命令

```bash
npm run validate:topics
npm run check
```

第一条命令检查 Topic Schema、目录命名、知识引用和当前解析对象数。第二条命令同时执行类型检查、全部测试、核心知识校验和 Topic 校验。
