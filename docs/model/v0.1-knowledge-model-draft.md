## 1. 本轮范围

本文件给出 v0.1 的字段、枚举、引用和校验规则，作为逐项评审的共同底稿。评审顺序为：

1. `Source`
2. `Provision`
3. `Requirement` 与 `Applicability`
4. `Decision`
5. `Control` 与 `ImplementationRule`
6. `Verification` 与 `EvidenceRequirement`

工程候选版已经配套提供 JSON Schema 和模型示例，用于在人工复核前发现结构问题。正式知识对象目录和发布内容仍需在模型通过复核后创建。

- Schema：[`schemas/v0.1/knowledge-object.schema.json`](../../schemas/v0.1/knowledge-object.schema.json)
- 示例：[`examples/model-v0.1/README.md`](../../examples/model-v0.1/README.md)

## 2. 总体约定

### 2.1 一个文件保存一个对象

后续结构化内容使用 YAML 编写，一个文件只保存一个核心对象。对象之间只通过稳定标识引用，发布清单记录本次发布包含的对象修订号和文件摘要。

计划中的存放方式为：

```text
knowledge/
  sources/<id>.yaml
  provisions/<id>.yaml
  requirements/<id>.yaml
  decisions/<id>.yaml
  controls/<id>.yaml
  verifications/<id>.yaml
```

本轮不创建这些目录。

### 2.2 标识

标识使用小写英文、数字和连字符，格式为：

```text
^(src|prv|req|dec|ctl|ver)-[a-z0-9]+(?:-[a-z0-9]+)*$
```

| 类型 | 前缀 | 示例 |
| --- | --- | --- |
| `Source` | `src-` | `src-eu-reg-2024-1774` |
| `Provision` | `prv-` | `prv-eu-reg-2024-1774-art-17-1-b` |
| `Requirement` | `req-` | `req-change-approval-independence` |
| `Decision` | `dec-` | `dec-change-role-separation-baseline` |
| `Control` | `ctl-` | `ctl-change-role-separation` |
| `Verification` | `ver-` | `ver-change-role-separation` |

标识规则：

- 标识在仓库和历史发布中全局唯一。
- 标识不包含对象修订号。
- 标题、措辞或文件路径变化时保持原标识。
- 同一知识含义发生修正时保留标识并增加 `revision`。
- 一项知识被拆分、合并或改变含义时创建新标识，并通过 `replaces` 指向被替代对象。
- `replaces` 只能指向同类型对象，替代关系不能形成环。

### 2.3 版本

v0.1 使用三层版本：

| 层级 | 字段或记录 | 用途 |
| --- | --- | --- |
| Schema 版本 | `schema_version` | 表示对象遵循的字段规范，使用 SemVer。首版目标值为 `0.1.0`。 |
| 对象修订号 | `revision` | 表示同一稳定标识下的内容修订，从 `1` 开始按整数递增。 |
| 发布版本 | 后续 Release Manifest | 固定一组对象修订号、文件摘要和工具版本，供历史任务复现。 |

同一发布中的引用只写稳定标识。发布清单负责固定每个标识对应的准确修订和 SHA-256 摘要。

### 2.4 工作语言

v0.1 的结构化知识正文使用英文，`language` 固定为 `en`。英文正文便于贴近 DORA 权威文本并减少翻译产生的含义变化。中文说明和后续阅读页面可以从同一对象生成，翻译内容不改变对象标识和监管含义。

### 2.5 单向引用

关系只在一个方向保存：

```text
Provision.source_id             -> Source
Requirement.provision_refs      -> Provision
Decision.subject_*_ids          -> Requirement / Control
Control.requirement_refs        -> Requirement
Verification.control_ids        -> Control
```

反向关系由校验或生成工具计算。对象中不保存无法限制目标类型的通用关系数组。

## 3. 通用字段

六类核心对象都包含以下字段：

```yaml
id: ctl-change-role-separation
type: control
schema_version: 0.1.0
revision: 1
title: Independent approval of ICT changes
language: en
lifecycle_status: draft
confirmation:
  status: not_required
  open_questions: []
replaces: []
```

| 字段 | 类型 | 必填 | 规则 |
| --- | --- | --- | --- |
| `id` | string | 是 | 满足标识格式，前缀与 `type` 一致，全局唯一。 |
| `type` | enum | 是 | `source`、`provision`、`requirement`、`decision`、`control`、`verification`。 |
| `schema_version` | SemVer string | 是 | 表示字段规范版本，v0.1 目标值为 `0.1.0`。 |
| `revision` | positive integer | 是 | 从 `1` 开始；已批准内容变化时递增。 |
| `title` | non-empty string | 是 | 简短说明对象内容，不承担规则正文职责。 |
| `language` | BCP 47 string | 是 | v0.1 固定为 `en`。 |
| `lifecycle_status` | enum | 是 | `draft`、`in_review`、`approved`、`superseded`、`retired`。 |
| `confirmation` | object | 是 | 表示内容是否需要有权人员作出实质决定。 |
| `replaces` | unique string array | 是 | 可以为空；每个标识必须指向同类型对象。 |

不设置 `created_at`、`updated_at`、作者和文件摘要字段。Git 保存文件变更历史，发布清单保存发布时间和摘要，避免同一事实重复维护。

### 3.1 生命周期状态

```text
draft -> in_review -> approved -> superseded
                         |
                         +-------> retired
```

| 状态 | 含义 |
| --- | --- |
| `draft` | 内容正在编写，可以修改。 |
| `in_review` | 内容进入人工评审，可以根据意见退回 `draft`。 |
| `approved` | 内容已完成所需评审，可以进入发布候选。 |
| `superseded` | 新对象或新修订已经替代当前内容。 |
| `retired` | 当前内容停止使用，且没有直接替代内容。 |

`approved` 表示对象具备进入发布候选的条件。实际发布状态由 Release Manifest 表达。

### 3.2 确认状态

```yaml
confirmation:
  status: pending
  open_questions:
    - Confirm whether the institution holds an EMD2 Article 9(1) exemption.
```

| 状态 | 含义 | 校验要求 |
| --- | --- | --- |
| `not_required` | 内容来自直接来源整理，或该对象本身就是人工决定；生命周期评审足以处理。 | `open_questions` 必须为空。 |
| `pending` | 存在需要有权人员判断的解释、适用性或实施问题。 | `open_questions` 至少一项。 |
| `confirmed` | 实质问题已有获批准的 `Decision`。 | `open_questions` 必须为空，并且至少一个获批准的 `Decision` 指向该对象。 |

`confirmation.status` 和 `confirmation.open_questions` 都是必填字段；问题列表为去重后的非空字符串数组。

v0.1 的类型限制：

- `Source`、`Provision`、`Decision` 和 `Verification` 使用 `not_required`。
- `Requirement` 和 `Control` 可以使用全部三种状态。
- `Decision` 是确认记录，其 `lifecycle_status` 达到 `approved` 后才具有确认效力。
- 已批准对象可以保留 `pending`，发布结果必须显式显示待确认问题。
- `Requirement` 的 `confirmed` 由 `interpretation` 或 `applicability` 决定支持。
- `Control` 的 `confirmed` 由 `implementation_choice` 决定支持。
- `exception` 和 `risk_acceptance` 记录受控偏离，不改变目标对象原有的确认状态。

## 4. Source

### 4.1 职责

`Source` 保存一份法规、监管文件、正式指引、主管机关材料或标准的身份、效力、版本、日期和官方位置。法律含义和工程结论进入后续对象。

### 4.2 字段

| 字段 | 类型 | 必填 | 规则 |
| --- | --- | --- | --- |
| `issuer_name` | non-empty string | 是 | 官方发布机构全称。 |
| `issuer_acronym` | string or null | 是 | 没有稳定缩写时使用 `null`。 |
| `jurisdictions` | unique string array | 是 | 至少一项；使用 `EU`、`EEA` 或 ISO 3166-1 alpha-2 国家代码。 |
| `document_type` | enum | 是 | 使用下方受控值。 |
| `authority_level` | enum | 是 | 使用下方受控值，区分法律效力和材料层级。 |
| `official_identifier` | non-empty string | 是 | 文件正式标识，例如 `Regulation (EU) 2024/1774`。 |
| `registry_identifiers` | array | 是 | 可以为空；保存 CELEX、EBA、MFSA 等登记标识。 |
| `version_label` | string or null | 是 | 记录版本号、合并文本或勘误处理范围。 |
| `official_url` | HTTPS URL | 是 | 直接指向发布机构或正式登记页面。 |
| `published_on` | ISO date | 是 | 官方发布日期。 |
| `effective_from` | ISO date or null | 是 | 生效日期；来源没有单独日期时使用 `null`。 |
| `applies_from` | ISO date or null | 是 | 开始适用日期；与生效日相同时也可以明确填写。 |
| `effective_to` | ISO date or null | 是 | 当前仍有效时使用 `null`。 |
| `retrieved_on` | ISO date | 是 | 最近一次核对官方来源的日期。 |
| `document_status` | enum | 是 | `current`、`superseded`、`withdrawn`、`unknown`。 |
| `source_relations` | array | 是 | 可以为空；只保存当前来源发出的类型化关系。 |

`document_type` 受控值：

- `eu_regulation`
- `eu_directive`
- `eu_delegated_regulation`
- `eu_implementing_regulation`
- `corrigendum`
- `esa_guideline`
- `national_legislation`
- `regulator_rule`
- `regulator_guidance`
- `official_webpage`
- `standard`

`authority_level` 受控值：

- `binding_law`
- `regulatory_guideline`
- `supervisory_guidance`
- `official_information`
- `supporting_standard`

`registry_identifiers` 每项包含：

```yaml
- registry: celex
  value: 32024R1774
```

| 子字段 | 类型 | 规则 |
| --- | --- | --- |
| `registry` | enum | `celex`、`eli`、`oj`、`eba`、`eiopa`、`esma`、`mfsa`、`legislation_mt`。 |
| `value` | non-empty string | 保存登记机构使用的准确值；纯数字值在 YAML 中需要加引号。 |

`source_relations` 每项包含：

```yaml
- relation: supplements
  source_id: src-eu-reg-2022-2554
```

| 子字段 | 类型 | 规则 |
| --- | --- | --- |
| `relation` | enum | `amends`、`corrects`、`supplements`、`implements`、`supersedes`、`references`。 |
| `source_id` | Source ID | 必须解析到另一个 `Source`。 |

允许的关系为 `amends`、`corrects`、`supplements`、`implements`、`supersedes`、`references`。反向关系由工具生成。

来源文件之间的 `supersedes` 表达正式文件关系；通用字段 `replaces` 表达仓库知识对象的替代关系。这两个关系处于不同层级。

### 4.3 专属校验

- `document_status: unknown` 不能进入 `approved`。
- `effective_to` 不能早于 `effective_from` 或 `applies_from`。
- `source_relations` 不能指向自身，目标必须是 `Source`。
- 相同 `registry` 与 `value` 的组合在同一来源中不能重复。
- `official_identifier`、登记标识、版本标签和 URL 共同确定所使用的文本，勘误合并范围必须能够从 `version_label` 和相关 `Source` 关系复现。

## 5. Provision

### 5.1 职责

`Provision` 保存来源中的精确位置和必要内容。一个对象只表达一个可以独立引用的条款位置，并且只属于一个 `Source`。

### 5.2 字段

| 字段 | 类型 | 必填 | 规则 |
| --- | --- | --- | --- |
| `source_id` | Source ID | 是 | 必须解析到一个 `Source`。 |
| `locator` | object | 是 | 保存人员可读标签和机器可检查的层级路径。 |
| `heading` | string or null | 是 | 原文没有独立标题时使用 `null`。 |
| `content_kind` | enum | 是 | `verbatim_excerpt` 或 `editorial_summary`。 |
| `content` | non-empty string | 是 | 保存必要摘录或忠于原文的摘要。 |

`locator` 示例：

```yaml
locator:
  label: Article 17(1)(b)
  segments:
    - kind: article
      value: "17"
    - kind: paragraph
      value: "1"
    - kind: point
      value: b
```

`segments.kind` 允许 `title`、`chapter`、`section`、`article`、`recital`、`rule`、`paragraph`、`point`、`subpoint`、`annex`、`page`、`other`。

| `locator` 子字段 | 类型 | 规则 |
| --- | --- | --- |
| `label` | non-empty string | 使用来源文件中可直接识别的位置标签。 |
| `segments` | non-empty array | 按来源层级顺序保存定位段。 |
| `segments[].kind` | enum | 使用上方受控值。 |
| `segments[].value` | non-empty string | 保留原文件中的编号或名称。 |

### 5.3 专属校验

- `locator.segments` 至少一项，顺序必须与原文层级一致。
- 同一 `source_id` 下的 `locator.label` 不能重复。
- `verbatim_excerpt` 必须保持原文语言和文字；`editorial_summary` 只能概括该位置明确包含的内容。
- 条款摘要不增加适用性、解释或工程实现结论。
- `Provision` 的确认状态固定为 `not_required`，内容准确性通过生命周期评审处理。

## 6. Requirement 与 Applicability

### 6.1 Requirement 职责

`Requirement` 将一个或多个条款整理成一项可以独立引用的义务、禁止、条件、许可或期限。正文需要写明承担者和应达到的结果，实施方法留给 `Control`。

### 6.2 Requirement 字段

| 字段 | 类型 | 必填 | 规则 |
| --- | --- | --- | --- |
| `statement` | non-empty string | 是 | 只表达一项可以独立判断的监管要求。 |
| `requirement_kind` | enum | 是 | `obligation`、`prohibition`、`condition`、`permission`、`deadline`。 |
| `derivation_type` | enum | 是 | `direct`、`combined`、`interpreted`。 |
| `provision_refs` | non-empty array | 是 | 类型化引用 `Provision`，至少一项 `direct_basis`。 |
| `applicability` | Applicability | 是 | 明确记录适用范围和有效时间。 |

`provision_refs` 每项包含：

```yaml
- provision_id: prv-eu-reg-2024-1774-art-17-1-b
  relation: direct_basis
```

每项只包含 `provision_id` 和 `relation`。`provision_id` 必须解析到 `Provision`，两个字段的组合在同一 `Requirement` 中唯一。

关系允许：

| 关系 | 用途 |
| --- | --- |
| `direct_basis` | 直接支持要求正文。 |
| `scope_basis` | 支持主体、地区、分支、日期或其他适用范围。 |
| `definition_basis` | 支持正文使用的定义。 |
| `supporting_context` | 提供监管说明或上下文，不单独承担要求依据。 |

`derivation_type` 含义：

| 值 | 含义 |
| --- | --- |
| `direct` | 忠于一个明确条款的单项整理。 |
| `combined` | 合并多个条款中可以机械拼合的条件，没有增加实质判断。 |
| `interpreted` | 加入了原文无法直接确定的解释，需要 `Decision`。 |

### 6.3 Applicability 字段

`Applicability` 内嵌在 `Requirement` 中：

```yaml
applicability:
  basis: source_defined
  jurisdictions:
    mode: include
    values: [EU]
  entity_types:
    mode: include
    values: [electronic_money_institution]
  license_roles:
    mode: include
    values: [emi_without_emd2_article_9_1_exemption]
  activities:
    mode: include
    values: [ict_change_management]
  products:
    mode: all
    values: []
  data_categories:
    mode: not_applicable
    values: []
  framework_branches:
    mode: include
    values: [dora_full_ict_risk_management]
  effective_from: "2025-01-17"
  effective_to: null
  conditions: []
  exclusions: []
```

| 字段 | 类型 | 必填 | 规则 |
| --- | --- | --- | --- |
| `basis` | enum | 是 | `source_defined`、`decision_defined`、`pending`。 |
| `jurisdictions` | ScopeSelector | 是 | 地区范围。 |
| `entity_types` | ScopeSelector | 是 | 主体类型。 |
| `license_roles` | ScopeSelector | 是 | 牌照状态或监管角色。 |
| `activities` | ScopeSelector | 是 | 业务或运营活动。 |
| `products` | ScopeSelector | 是 | 产品范围。 |
| `data_categories` | ScopeSelector | 是 | 数据范围。 |
| `framework_branches` | ScopeSelector | 是 | 例如 DORA 完整或简化 ICT 风险管理框架。 |
| `effective_from` | ISO date or null | 是 | 要求开始适用的日期。 |
| `effective_to` | ISO date or null | 是 | 持续适用时使用 `null`。 |
| `conditions` | unique string array | 是 | 可以为空；保存额外适用条件。 |
| `exclusions` | unique string array | 是 | 可以为空；保存来源支持的排除条件。 |

`basis` 含义：

- `source_defined`：适用范围可以由公开来源直接确定。
- `decision_defined`：适用范围依赖获批准的 `Decision`。
- `pending`：当前事实或解释不足，尚未形成适用结论。

每个 `ScopeSelector` 使用同一结构：

```yaml
mode: include
values:
  - electronic_money_institution
```

| `mode` | 含义 | `values` 规则 |
| --- | --- | --- |
| `all` | 该维度内全部值适用。 | 必须为空。 |
| `include` | 只包含列出的值。 | 至少一项。 |
| `exclude` | 除列出值外均适用。 | 至少一项。 |
| `not_applicable` | 该维度不参与本要求的适用判断。 | 必须为空。 |
| `unknown` | 该维度尚未判断。 | 必须为空。 |

`all` 表示已经确认该维度内全部值都适用，`not_applicable` 表示该维度不参与适用判断，`unknown` 表示仍缺少结论。三者必须严格区分。各维度的 `values` 使用 Schema 中声明的受控词汇，不能写自由文本。

v0.1 首条知识链使用以下最小词汇：

| 维度 | 初始值 |
| --- | --- |
| `jurisdictions` | `EU`、`MT`；其他地区使用经过校验的 ISO 3166-1 alpha-2 代码。 |
| `entity_types` | `financial_entity`、`electronic_money_institution`。 |
| `license_roles` | `emi_without_emd2_article_9_1_exemption`、`emi_with_emd2_article_9_1_exemption`。 |
| `activities` | `ict_risk_management`、`ict_change_management`。 |
| `products` | `electronic_money`、`payment_service`。 |
| `data_categories` | `personal_data`、`payment_data`、`authentication_data`、`operational_data`。 |
| `framework_branches` | `dora_full_ict_risk_management`、`dora_simplified_ict_risk_management`。 |

新增词汇需要先说明来源和使用场景，再更新 Schema 与词汇测试。`all` 和 `not_applicable` 不需要虚构一个占位值。

### 6.4 专属校验

- `statement` 只包含一项要求；可以独立失败的并列义务需要拆分。
- `provision_refs` 至少包含一项 `direct_basis`，引用目标必须是 `Provision`。
- `applicability.basis: source_defined` 时至少包含一项 `scope_basis`；同一 `Provision` 可以分别承担直接依据和范围依据，`provision_id` 与 `relation` 的组合不能重复。
- `derivation_type: combined` 时至少包含两个 `direct_basis`。
- `derivation_type: interpreted` 时，`confirmation.status` 只能是 `pending` 或 `confirmed`；`confirmed` 必须存在获批准的 `interpretation` 类型 `Decision`。
- `applicability.basis: decision_defined` 时，要求必须为 `confirmed`，并且有获批准的 `applicability` 类型 `Decision` 指向该要求。
- `applicability.basis: pending` 时，要求必须为 `pending`。
- `mode: unknown` 只允许出现在 `applicability.basis: pending` 中。
- `effective_to` 不能早于 `effective_from`。
- `conditions` 和 `exclusions` 不能包含相同文字。

## 7. Decision

### 7.1 职责

`Decision` 保存有权人员对解释、适用性、例外、实施选择或风险接受作出的明确决定。它只指向 `Requirement` 或 `Control`，并记录问题、结论、理由、权限角色和有效时间。

### 7.2 字段

| 字段 | 类型 | 必填 | 规则 |
| --- | --- | --- | --- |
| `decision_type` | enum | 是 | `interpretation`、`applicability`、`exception`、`implementation_choice`、`risk_acceptance`。 |
| `subject_requirement_ids` | unique Requirement ID array | 是 | 可以为空。 |
| `subject_control_ids` | unique Control ID array | 是 | 可以为空。 |
| `question` | non-empty string | 是 | 说明需要作出的判断。 |
| `conclusion` | non-empty string | 是 | 说明已经确认的结论。 |
| `rationale` | non-empty string | 是 | 说明结论依据、权衡和边界。 |
| `basis_provision_ids` | unique Provision ID array | 是 | 可以为空；法律解释或适用性决定至少一项。 |
| `assumptions` | unique string array | 是 | 可以为空；保存决定依赖的事实假设。 |
| `conditions` | unique string array | 是 | 可以为空；保存决定成立的附加条件。 |
| `decided_by_role` | non-empty string | 是 | 保存有权角色，不在公共仓库保存个人敏感信息。 |
| `decided_on` | ISO date | 是 | 作出决定的日期。 |
| `effective_from` | ISO date | 是 | 决定开始有效的日期。 |
| `effective_to` | ISO date or null | 是 | 持续有效时使用 `null`。 |
| `review_due_on` | ISO date or null | 是 | 没有固定复核日期时使用 `null`。 |

### 7.3 专属校验

- `subject_requirement_ids` 和 `subject_control_ids` 合计至少一项。
- `interpretation` 和 `applicability` 必须至少指向一个 `Requirement`，并至少引用一个 `Provision`。
- `implementation_choice` 必须至少指向一个 `Control`。
- `effective_to` 不能早于 `effective_from`；`review_due_on` 不能早于 `decided_on`。
- `Decision` 的确认状态固定为 `not_required`。
- 只有 `lifecycle_status: approved` 的决定可以使目标对象达到 `confirmed`。
- `interpretation` 和 `applicability` 可以支持 `Requirement` 的 `confirmed`；`implementation_choice` 可以支持 `Control` 的 `confirmed`。
- `exception` 和 `risk_acceptance` 不满足目标对象的确认条件。
- 机构内部决定、监管往来和个人身份记录进入私有知识层；公共仓库只保存可公开的通用决定和脱敏示例。

## 8. Control 与 ImplementationRule

### 8.1 Control 职责

`Control` 保存为满足一个或多个 `Requirement` 而设计的可检查结果、责任角色、运行时机和具体实施规则。

### 8.2 Control 字段

| 字段 | 类型 | 必填 | 规则 |
| --- | --- | --- | --- |
| `objective` | non-empty string | 是 | 描述可以被观察或检查的结果。 |
| `requirement_refs` | non-empty array | 是 | 类型化引用 `Requirement`，至少一项 `implements`。 |
| `control_category` | enum | 是 | `governance`、`process`、`technical`、`operational`。 |
| `control_functions` | unique enum array | 是 | 至少一项；`preventive`、`detective`、`corrective`、`recovery`。 |
| `owner_role` | non-empty string | 是 | 保存通用责任角色。 |
| `operation_mode` | enum | 是 | `event_driven`、`scheduled`、`continuous`、`on_demand`。 |
| `trigger_or_frequency` | non-empty string | 是 | 说明控制何时触发或多长时间执行一次。 |
| `implementation_rules` | non-empty ImplementationRule array | 是 | 具体说明流程、权限、数据、接口、配置、运维和异常处理。 |

`requirement_refs` 每项包含：

```yaml
- requirement_id: req-change-approval-independence
  relation: implements
```

每项只包含 `requirement_id` 和 `relation`。`requirement_id` 必须解析到 `Requirement`，两个字段的组合在同一 `Control` 中唯一。

关系允许：

- `implements`：该控制直接实现要求。
- `supports`：该控制提供辅助保障，不能单独覆盖要求。

### 8.3 ImplementationRule 字段

| 字段 | 类型 | 必填 | 规则 |
| --- | --- | --- | --- |
| `key` | local identifier | 是 | 在所属 `Control` 内唯一，使用小写英文、数字和连字符。 |
| `rule_type` | enum | 是 | `process`、`access`、`data`、`interface`、`configuration`、`operations`、`exception`。 |
| `statement` | non-empty string | 是 | 描述一项具体实施规则。 |
| `parameter_status` | enum | 是 | `not_applicable`、`fixed`、`institution_defined`、`pending`。 |
| `parameters` | array | 是 | 可以为空；每项包含 `name`、`value` 和 `unit`。 |
| `conditions` | unique string array | 是 | 可以为空；保存规则触发条件。 |
| `failure_handling` | non-empty string | 是 | 说明规则无法满足时的阻断、升级或恢复行为。 |
| `open_questions` | unique string array | 是 | 可以为空；保存尚未确定的实施问题。 |

参数示例：

```yaml
parameters:
  - name: maximum_emergency_review_delay
    value: 2
    unit: business_days
```

| 参数子字段 | 类型 | 规则 |
| --- | --- | --- |
| `name` | local identifier | 在当前规则中唯一。 |
| `value` | string, number, boolean or null | 固定参数必须有值；待机构确定时可以为 `null`。 |
| `unit` | string or null | 没有单位时使用 `null`。 |

`parameter_status` 校验：

- `not_applicable`：`parameters` 和 `open_questions` 必须为空。
- `fixed`：`parameters` 至少一项，每个 `value` 都有明确值，`open_questions` 为空。
- `institution_defined`：`parameters` 至少一项，`value` 可以为 `null`，用于标出机构实施时必须补充的参数。
- `pending`：`open_questions` 至少一项，所属 `Control` 的确认状态必须为 `pending`。

### 8.4 专属校验

- `requirement_refs` 至少一项使用 `implements`。
- 同一控制中的 `implementation_rules.key` 不能重复。
- 一个规则只表达一个可独立实现和失败的约束。
- 所有规则都必须说明失败处理。
- 所属角色、执行时机或失败处理明显不同的控制需要拆分。
- `confirmation.status: confirmed` 时，至少一个获批准的 `implementation_choice` 类型 `Decision` 必须指向该控制。

## 9. Verification 与 EvidenceRequirement

### 9.1 Verification 职责

`Verification` 保存检查或测试一个或多个 `Control` 的方法、执行者、步骤、预期结果、失败条件、失败处理和所需证据。

### 9.2 Verification 字段

| 字段 | 类型 | 必填 | 规则 |
| --- | --- | --- | --- |
| `control_ids` | unique Control ID array | 是 | 至少一项，目标必须是 `Control`。 |
| `verification_type` | enum | 是 | `inspection`、`test`、`query`、`review`、`observation`。 |
| `execution_mode` | enum | 是 | `manual`、`automated`、`hybrid`。 |
| `executor_role` | non-empty string | 是 | 保存检查或测试责任角色。 |
| `operation_mode` | enum | 是 | `event_driven`、`scheduled`、`continuous`、`on_demand`。 |
| `trigger_or_frequency` | non-empty string | 是 | 说明何时执行检查或测试。 |
| `preconditions` | unique string array | 是 | 可以为空。 |
| `procedure` | ordered non-empty string array | 是 | 按顺序保存可重复执行的步骤。 |
| `expected_result` | non-empty string | 是 | 明确通过条件。 |
| `failure_criteria` | non-empty string array | 是 | 明确哪些结果构成失败。 |
| `on_failure` | non-empty string | 是 | 说明阻断、升级、修复和重新验证要求。 |
| `evidence_requirements` | non-empty EvidenceRequirement array | 是 | 说明需要取得并检查的制品。 |

### 9.3 EvidenceRequirement 字段

| 字段 | 类型 | 必填 | 规则 |
| --- | --- | --- | --- |
| `key` | local identifier | 是 | 在所属 `Verification` 内唯一。 |
| `artifact_type` | enum | 是 | `change_record`、`approval_record`、`audit_log`、`test_report`、`configuration_snapshot`、`document`、`ticket`、`other`。 |
| `description` | non-empty string | 是 | 说明证据内容和用途。 |
| `required_fields` | unique non-empty string array | 是 | 列出证据必须包含的信息。 |
| `source_status` | enum | 是 | `known`、`institution_defined`、`pending`。 |
| `source_system` | string or null | 是 | 已知来源系统时填写。 |
| `retention_status` | enum | 是 | `fixed`、`institution_defined`、`pending`、`not_applicable`。 |
| `retention_period` | ISO 8601 duration or null | 是 | 例如 `P5Y`；尚未确定或不适用时使用 `null`。 |
| `data_classifications` | unique enum array | 是 | 至少一项；`public`、`internal`、`confidential`、`personal_data`、`restricted`。 |
| `redaction_required` | boolean | 是 | 表示证据导出或共享时是否需要脱敏。 |
| `open_questions` | unique string array | 是 | 可以为空。 |

### 9.4 专属校验

- `procedure` 的数组顺序就是执行顺序，不能使用无顺序语义的集合替代。
- `failure_criteria` 必须能够直接对照 `expected_result`。
- 同一检查中的 `evidence_requirements.key` 不能重复。
- `source_status: known` 时 `source_system` 必填；`institution_defined` 和 `pending` 可以使用 `null`。
- `retention_status: fixed` 时 `retention_period` 必填；其他状态使用 `null`。
- 固定保留期限必须能够通过关联 `Control` 回到相应 `Requirement` 或获批准的 `implementation_choice`，不能只在证据模板中写入一个无依据期限。
- `source_status` 或 `retention_status` 为 `pending` 时，`open_questions` 至少一项。
- `EvidenceRequirement` 只描述所需证据，实际日志、审批记录、客户数据和生产制品不进入公共仓库。
- `Verification` 的确认状态固定为 `not_required`；需要人工选择的实施参数放在关联 `Control` 或 `Decision` 中。

## 10. 跨对象校验

### 10.1 JSON Schema 负责

- 必填字段、字段类型、字符串格式和枚举值。
- `additionalProperties: false`，拒绝未知字段。
- 标识前缀与对象 `type` 的对应关系。
- 数组最小数量、数组内去重和内嵌结构必填字段。
- 日期、SemVer、HTTPS URL 和 ISO 8601 duration 的基本格式。
- `ScopeSelector`、确认状态和参数状态的条件分支。

### 10.2 TypeScript 图校验器负责

- 全仓库标识唯一。
- 所有引用均可解析，并且目标类型正确。
- 同一发布候选中的引用解析到本次固定的对象修订。
- `approved` 对象只依赖 `approved` 对象。
- `confirmed` 的 `Requirement` 存在指向它的获批准 `interpretation` 或 `applicability` 决定。
- `confirmed` 的 `Control` 存在指向它的获批准 `implementation_choice` 决定。
- `replaces` 不形成环。
- `Source -> Provision -> Requirement -> Control -> Verification` 的来源链完整。
- `Requirement` 至少一个直接条款依据，`Control` 至少一个直接实现关系，`Verification` 至少一个控制和证据要求。
- ID、修订号和历史发布之间符合不可变规则。
- 公共仓库文件不包含已配置的敏感字段、凭据模式或实际证据制品。

### 10.3 发布前内容检查

- 未知枚举、断裂引用和重复标识直接失败。
- `pending` 内容可以进入明确标注的来源基线或工程基线，发布清单必须列出全部待确认问题。
- 具有机构适用性、风险接受或例外结论的内容缺少获批准 `Decision` 时直接失败。
- 每次发布至少保存 Schema 版本、对象清单、对象修订、文件摘要、来源基线和校验工具版本。

## 12. 工程审查结论

2026-09-02 对六类对象完成了一轮工程审查，结论如下：

| 对象 | 结论 | 本轮处理 |
| --- | --- | --- |
| `Source` | 字段足以固定文件身份、版本、效力和官方位置。 | Schema 约束 HTTPS 地址、日期、状态、登记标识和来源关系。 |
| `Provision` | 精确位置与必要内容分开表达，能够支持后续引用。 | Schema 约束条款层级、内容类型和单一来源。 |
| `Requirement` | 可以区分直接整理、机械组合和需要解释的要求。 | 示例增加适用日期，并明确 `all`、`not_applicable` 和 `unknown` 的差别。 |
| `Decision` | 可以记录解释、适用性和实施选择，同时保留权限与有效期。 | Schema 约束不同决定类型允许指向的对象。 |
| `Control` | 控制目标、责任、运行时机和实施规则职责清楚。 | Schema 约束参数状态、失败处理和直接实现关系。 |
| `Verification` | 检查方法、通过条件、失败处理和证据要求可以形成闭环。 | Schema 约束执行步骤、失败条件、证据来源和保留状态。 |

模型示例使用 Regulation (EU) 2024/1774 Article 17(1)(a)、(b) 和 (g) 三项真实要求检查字段表达能力，并用 Article 17(1)(b) 建立一条完整的 `Source -> Provision -> Requirement -> Control -> Verification` 链。示例只用于模型验证，内容状态和适用结论不构成 v0.1 正式知识发布。

JSON Schema 负责单对象结构约束。重复标识、断裂引用、目标类型、确认关系、替代环和发布历史等全局规则由第 6 步的 TypeScript 图校验器负责。

## 13. 人工复核出口

每类对象的人工复核需要确认四项：

1. 对象职责是否清楚，是否与相邻对象重复。
2. 字段是否达到首条 DORA ICT 变更管理知识链所需的最小集合。
3. 枚举、状态和引用规则能否由 Schema 或图校验器确定执行。
4. 示例能否覆盖真实使用，同时保持公共知识、机构决定和实际证据的边界。

六类对象全部确认后固定 Schema 候选版，并进入第 5 步正式知识内容建设。Schema 失败用例和跨对象引用检查在第 6 步纳入自动化测试。
