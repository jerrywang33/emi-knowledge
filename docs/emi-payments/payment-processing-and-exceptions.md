# 支付处理与异常：普通 SEPA 转账

本文用一笔普通 SEPA 欧元转账（SCT）说明支付怎样处理、记录如何关联，以及遇到异常时需要先查清什么。用户已确认学习范围；机构实际产品、PSP 和清算接入方式尚未确定。

## 1. 范围与阅读方式

样例限于 EU/EEA 内、无换汇的单笔电子发起普通 SCT，从付款侧观察处理过程。不包含 SCT Inst、卡支付、直接借记、批量支付、PISP 接入和具体清算设施的操作细节。

正文分为三种内容：

- **来源说明**：带官方文件定位，用于理解方案术语与流程。
- **工程建议**：本仓库提出的记录与处理方法，供后续设计、评审和测试。
- **待确认事项**：需要产品、业务、合规、财务或渠道资料才能确定，正文不代填。

开户、客户授权、SCA、收款人验证（VoP）、AML/CFT、制裁、客户资金保护及数据保护仍是依赖。本轮未复核这些依赖的完整适用性；学习范围的排除项不代表实际产品可以省略相应检查。

## 2. 先认识参与方

**来源说明。** 主要角色是付款人、付款方支付服务商（Originator PSP）、收款方支付服务商（Beneficiary PSP）和收款人；清算与结算机制（CSM）及中间 PSP 支持服务商之间的处理。方案参与与清算接入分别确认。依据：[SCT Rulebook 第 3 章](https://www.europeanpaymentscouncil.eu/sites/default/files/kb/file/2025-09/EPC125-05%202025%20SCT%20Rulebook%20version%201.1.pdf#page=23)。

学习时可代入“A 向 B 支付 100 EUR”：A 提交指令，付款方 PSP 执行付款，收款方 PSP 为 B 入账，B 接收款项。CSM 支持 PSP 之间的处理；它可能包含不同的清算与结算服务提供方。

**待确认。** EMI 在真实产品中承担哪个角色、由谁提供付款账户、谁加入方案、谁发送消息与处理异常，需要逐项记录。持有 EMI 牌照不能在本样例中被当作已完成这些安排的证明。

## 3. 正常流程

**来源说明。** 简化过程如下，依据：[SCT Rulebook 4.3.1](https://www.europeanpaymentscouncil.eu/sites/default/files/kb/file/2025-09/EPC125-05%202025%20SCT%20Rulebook%20version%201.1.pdf#page=28)。

```text
付款人提交指令
  -> 付款方 PSP 检查指令
  -> 付款方 PSP 扣款并发送，经所选 CSM 处理与结算
  -> 收款方 PSP 入账并向收款人提供信息
```

**工程建议。** 记录每个阶段已经获得的事实，不用一个含义不明的“成功”代替全部结果：

| 观察位置 | 建议保存的事实 | 仍需核实的问题 |
| --- | --- | --- |
| 客户提交 | 请求标识、付款意图、金额币种、收款信息版本、授权与准入检查引用 | 请求能否进入执行流程？ |
| 本地受理 | 业务单号、检查结果、选定渠道、余额与账务处理引用 | 本地保存成功是否已经触发外部发送？ |
| 对外发送 | 每次发送的标识、内容摘要、发送时间、渠道答复和外部关联号 | 对方答复具体确认了哪一阶段？ |
| 外部处理 | 已核实的处理、结算或收款入账信息及其来源 | 哪些信息当前拿不到，如何查询？ |
| 后续核对 | 业务记录、账务记录与外部流水的对应关系及差异 | 记录是否完整，是否需要调查或修复？ |

客户界面的状态文案应对应可证明的阶段。具体渠道答复、结算确认和收款入账确认如何映射，保留到接口与业务规则评审时确定。

例如 HTTP `200` 只按接口契约解释，不能直接映射成“收款人已到账”。PSP 间结算、收款人入账和本地账务完成分别记录；“处理中”“结果待确认”等文案仅为讨论示例，不构成统一状态机。

## 4. 异常术语要分开

**来源说明。** 下表用于分辨流程，不代替完整发起条件、时限和消息规则。

| 名称 | 基本含义 | 定位 |
| --- | --- | --- |
| Reject，拒绝 | PSP 间结算前，指令未被接受进入正常执行。 | [Rulebook 4.3.2.1](https://www.europeanpaymentscouncil.eu/sites/default/files/kb/file/2025-09/EPC125-05%202025%20SCT%20Rulebook%20version%201.1.pdf#page=29) |
| Return，退回 | PSP 间结算后，收款方 PSP 无法正常执行并退回交易。 | [Rulebook 4.3.2.2](https://www.europeanpaymentscouncil.eu/sites/default/files/kb/file/2025-09/EPC125-05%202025%20SCT%20Rulebook%20version%201.1.pdf#page=30) |
| Recall，召回 | 付款方 PSP 按规则限定的重复发送、技术错误或欺诈原因发起召回。 | [Clarification Paper 2.9](https://www.europeanpaymentscouncil.eu/sites/default/files/kb/file/2025-10/EPC131-17%20v4.0%20Clarification%20Paper%20SCT%20and%20SCT%20Inst%20scheme%20rulebooks.pdf#page=11) |
| RFRO，付款人请求召回 | 付款人因其他原因请求取回已结算转账；成功取回取决于相关答复与收款人同意。 | [Rulebook 4.3.2.4](https://www.europeanpaymentscouncil.eu/sites/default/files/kb/file/2025-09/EPC125-05%202025%20SCT%20Rulebook%20version%201.1.pdf#page=35) |
| SCT Inquiry，调查 | 处理未到账或起息日更正的调查；与发起资金退回分别处理。 | [Rulebook 4.4](https://www.europeanpaymentscouncil.eu/sites/default/files/kb/file/2025-09/EPC125-05%202025%20SCT%20Rulebook%20version%201.1.pdf#page=38) |

收款人已经入账后自愿转回资金，按新的转账处理，不使用普通 Return，见 [Clarification Paper 3.1](https://www.europeanpaymentscouncil.eu/sites/default/files/kb/file/2025-10/EPC131-17%20v4.0%20Clarification%20Paper%20SCT%20and%20SCT%20Inst%20scheme%20rulebooks.pdf#page=17)。Recall / RFRO 的肯定答复有各自流程，不能与自愿发起的新转账混用，见 [2.9](https://www.europeanpaymentscouncil.eu/sites/default/files/kb/file/2025-10/EPC131-17%20v4.0%20Clarification%20Paper%20SCT%20and%20SCT%20Inst%20scheme%20rulebooks.pdf#page=11)。

原因码需要连同异常类型、发起方和原交易理解，并考虑来源明确列出的披露限制。原因码指引中的建议处理动作也需要结合实际条件判断。依据：[Reason Code Guidance 第 1-3 节](https://www.europeanpaymentscouncil.eu/sites/default/files/kb/file/2024-11/EPC135-18%20v6.0%20Guidance%20on%20Reason%20Codes%20for%20SCT%20R-transactions.pdf#page=2)。

### 4.1 召回的条件与跟进

**来源说明。** 下表只摘出本轮案例需要理解的时间条件，保留各自起算事件。依据：[Rulebook 4.3.2.3、4.3.2.4](https://www.europeanpaymentscouncil.eu/sites/default/files/kb/file/2025-09/EPC125-05%202025%20SCT%20Rulebook%20version%201.1.pdf#page=31)、[Clarification Paper 2.9](https://www.europeanpaymentscouncil.eu/sites/default/files/kb/file/2025-10/EPC131-17%20v4.0%20Clarification%20Paper%20SCT%20and%20SCT%20Inst%20scheme%20rulebooks.pdf#page=11)和 [2.12](https://www.europeanpaymentscouncil.eu/sites/default/files/kb/file/2025-10/EPC131-17%20v4.0%20Clarification%20Paper%20SCT%20and%20SCT%20Inst%20scheme%20rulebooks.pdf#page=13)。

| 事项 | 需要区分的时间条件 |
| --- | --- |
| 重复发送或技术错误的 Recall | 发起窗口为 10 个银行营业日；按 2.12 的说明，从原交易执行日后的银行营业日开始计数。 |
| 欺诈原因的 Recall | 发起窗口为 13 个月；同样按 2.12 确认起算点，不能改成从发现问题之日计算。 |
| RFRO 的原交易资格 | 原交易扣款日须落在付款方 PSP 收到客户请求之前的 13 个月内。这是原交易的回溯条件，不能套用 Recall 发起窗口。 |
| 收款方 PSP 答复 Recall / RFRO | 15 个银行营业日；按 2.12，从收到请求的银行营业日之后的银行营业日开始计数。 |

规则分别限制同一原交易不能重复发起 Recall 或重复发起 RFRO；另一流程的资格仍需单独判断，不能通过换名称绕过原流程限制。超过答复期限仍无收款方 PSP 答复时，规则提供 Request for Status Update 跟进路径，不允许因此重复发起同一 Recall / RFRO。否定答复、没有答复、资金已取回分别处理。依据：[Rulebook 4.3.2.3、4.3.2.4](https://www.europeanpaymentscouncil.eu/sites/default/files/kb/file/2025-09/EPC125-05%202025%20SCT%20Rulebook%20version%201.1.pdf#page=31)。

**待确认。** 银行营业日历、收到时间的认定、时区、截止时间和渠道操作方式仍需确定；本表不能直接作为日期计算程序。正常执行、Reject、Return、Inquiry 及客户退款的完整期限规则仍待单独整理，不能套用上表。

### 4.2 渠道资金取回与客户退款

**来源说明。** EPC 在 [Clarification Paper 2.10](https://www.europeanpaymentscouncil.eu/sites/default/files/kb/file/2025-10/EPC131-17%20v4.0%20Clarification%20Paper%20SCT%20and%20SCT%20Inst%20scheme%20rulebooks.pdf#page=13)说明，付款方 PSP 可能在召回完成前，已依据另行适用的客户退款义务向客户返还资金。本稿只保留这项区别，PSD2 具体义务、例外及 Malta 适用性仍待法律专题复核。

**工程建议。** 客户退款和渠道资金取回分别关联依据与账务记录。不要用“召回仍在等待”自动推迟客户处理；渠道资金后来取回时，先检查客户是否已获退款，避免再次调整同一笔客户余额。机构先行退款也不能被写成“渠道召回已成功”。

## 5. 系统中建议保留哪些记录

本节全部为**工程建议**，字段名用于讨论，不表示 EPC 字段、强制 Schema 或既定数据库设计。

| 记录 | 用途 |
| --- | --- |
| 业务支付记录 `payment_id` | 关联一次明确的付款意图、金额币种、参与方与输入版本。 |
| 发送尝试 `attempt_id` | 区分每次付款发送，保留内容和通信结果；查单、召回等操作另外标明操作类型及所关联的业务或案件，不能把所有调用都计成付款次数。 |
| 外部关联号 `external_reference` | 按提供方和消息类型保存原值，用于查单和对账；不能假定任意外部字段全局唯一。 |
| 处理事件 `event_id` | 保存渠道来源、原始状态、事件时间、收到时间、关联对象与去重结果。 |
| 账务关联 `ledger_reference` | 关联预留、扣账、释放、退回或调整记录；是否采用预留、科目和记账时点由机构确认。 |
| 异常案件 `case_id` | 保存调查、召回、答复、资金结果、负责人、截止时间和决定依据。 |

这些是信息职责，不要求建立六张表或六个服务。标识按机构、渠道账户和业务类型等适用范围解释，不能只凭字符串相同合并记录。保存本地事件编号也不自动解决重复识别，仍需渠道事件标识和内容比对规则。

建议分别记录通信结果、支付处理进度、账务处理情况和异常案件进度。例如“召回请求已发送”仅更新案件进度，不能直接产生“资金已取回”的账务事实。

资金记录应说明反映的是客户余额、内部账务还是 PSP 间资金变化。对账时核对记录之间的对应关系，避免把不同含义的余额混作一个数；本稿不规定统一余额公式、会计分录或客户资金保护处理。

原始报文、个人数据和真实账务记录保存在机构允许的私有环境，按确认后的访问与保留规则管理。公共案例只用合成标识；排查问题时也不能把客户报文复制到公共仓库。

## 6. 超时、重复与记录不一致怎么讨论

本节为**工程建议**，执行前需要渠道契约、权限与机构规则支持。

### 6.1 提交超时或结果未知

1. 保留原业务单号、发送尝试和内容摘要，核实超时发生在哪一段通信。
2. 检查是否已有可信的渠道关联号、查询结果、处理事件或对账记录，记录仍未知的部分。
3. 按渠道明确提供的查询或安全重试约定处理。未确认该约定时，不因超时换一个业务标识再次付款。
4. 为未解决事项指定负责人和跟进期限，必要时进入渠道调查与客户沟通。资金释放和客户处理遵循另行确认的规则，不用“未知”无限期搁置。

超时只说明未及时取得答复。渠道未收到、正在处理、已经处理但答复丢失都可能发生。查询“未找到”时，核对查询范围、数据可见延迟和结果含义；在渠道没有明确保证前，不能把它当成未执行的证明。换渠道发送也可能重复付款，遵循同样的检查。

允许重试前需要明确渠道幂等标识的作用范围、有效期、输入一致性和并发行为；只沿用本地业务单号无法保证外部只执行一次。

应用超时计时与方案业务期限分别管理。第 4.1 节提供部分来源条件，实际期限仍需结合业务起算点、营业日历、截止时间和升级要求确认；当前草案不提供可执行的日期计算规则。

### 6.2 重复提交与重复事件

同一业务标识和相同输入再次出现时，先返回或查询已有处理结果；同一标识对应不同金额或收款信息时，作为输入冲突处理。只有渠道契约明确支持时才按其约定重发，不把本地去重等同于外部一定只执行一次。

查询已有记录和决定是否创建发送任务之间需要防止并发重复，例如使用同一作用范围内的唯一约束及原子写入。采用哪种实现由项目决定；“先查再发”的两步文字描述本身不保证安全。

对重复通知，先确认是否为同一业务事件，再避免重复记账。新通知携带了更正信息时应保留差异并评估，不能仅凭相同业务单号丢弃。迟到事件按事实更新或进入冲突调查，不能只依收到顺序覆盖状态。

先核对通知来源、机构和渠道账户、原交易及事件类型，再决定是否使用。无法验证或关联不清的通知进入受限的待核对记录，不直接改变余额。“通知已保存”和“账务已应用”分别记录：第一次处理若中断，后续重复通知应触发安全恢复或核查，不能因曾经收到而永久跳过；恢复时也要先查明账务是否已经提交，避免再次应用。去重、账务提交及完成标记之间的并发和中断行为需要项目测试验证。

### 6.3 外部已处理，内部记录不一致

暂停针对该笔交易的无依据再次付款，先核对外部信息的含义、真实性及关联关系，再修复遗漏的本地记录。若已经形成两笔真实外部交易，不能通过删除内部记录把它们合成一笔，应分别跟踪处置与资金结果。

修复记录保留原结果、补充依据、执行者与复核结果。业务状态修正不直接触发再次扣账；按已存在的账务记录判断需要补做还是仅补齐关联。外部记录缺少可核实的阶段信息时，继续调查，不把笼统的“已处理”提升为“收款人已到账”。

### 6.4 退回与召回的本地处理

异常案件至少区分请求、答复、资金变化和客户账务处理。发起操作前核对所用流程的资格与期限；收到答复后核对原交易、金额、已处理记录和资金结果，再依批准的账务规则处理。客户退款义务按第 4.2 节单独判断，不以渠道资金取回作为统一前提。

案件中保留原付款、相关资金转回及已有客户退款的对应关系。相同金额不能独自证明两份记录对应同一笔钱；金额不同则保留差异，查清费用或其他依据，不能自动补齐。Agent 可以整理材料和提出候选操作，不获得外部发送、扣账或风险接受的默认权限。

## 8. 案例与检查结果

下列合成案例的已知事实、判断依据、建议动作、禁止动作和待确认项，已写入[案例与文档检查结果](payment-processing-and-exceptions-cases.md)。作者 Agent 已逐项核对正文能否支持回答，并据此修订说明；这属于文档自查，不是独立人员或 Agent 使用验收，也没有执行渠道或账务测试。未形成 `scenarios/` 场景包。

| 编号 | 输入情形 | 检查的问题 |
| --- | --- | --- |
| SCT-01 | 一笔 100 EUR 请求，依次取得渠道受理、外部处理、收款信息和本地账务记录。 | 每份记录证明哪个阶段？关联是否一致？对外文案有没有超出证据？ |
| SCT-02 | 相同业务标识、相同输入连续提交两次。 | 如何找到已有尝试？有什么依据允许或禁止再次发送？ |
| SCT-03 | 相同业务标识第二次把金额改为 200 EUR。 | 能否识别输入冲突并保留两份输入，避免静默修改原指令？ |
| SCT-04 | 发送后超时，外部是否收到未知。 | 还缺什么事实？向谁查询？如何避免无依据新增付款和无限期悬置？ |
| SCT-05 | 同一渠道事件重复到达，随后又出现含义冲突的迟到事件。 | 哪些属于重复，哪些需要调查？账务如何避免再次应用同一结果？ |
| SCT-06 | 外部记录显示已处理，本地应用此前因异常标记失败。 | 如何核实外部记录、修复本地状态并避免再次付款？ |
| SCT-07 | 分别收到结算前拒绝与结算后退回信息。 | 能否分清异常流程、资金事实和本地后续处理，避免仅按“失败”统一退款？ |
| SCT-08 | 召回已发出，收到否定答复或暂未收到答复。 | 案件处于什么阶段？哪些查询、期限和授权尚需核对？为什么不能记为已取回？ |
| SCT-09 | 收款人已入账并自愿转回，另有一笔 RFRO 等待答复。 | 能否区分新的转账与召回相关流程，保留各自交易和案件关联？ |
| SCT-10 | 实际出现两笔外部付款，随后一笔相关资金转回通知重复到达。 | 能否分别保留两笔付款、一次真实资金转回及重复通知，避免重复调整余额？ |

| --- | --- | --- | --- |

| SCT-Q2 | 状态、标识、查询、幂等和消息 | 复核 EPC 接口指引及选定渠道的公开契约；本轮未建立 ISO 20022 字段与原因码完整映射。 | 渠道选择、接口版本、私有补充条款、账户作用范围和实测结果。 |
| SCT-Q3 | 余额、记账、释放与调整 | 补充“账务与对账”通用说明和合成案例；本轮已区分资金与记录。 | 财务与业务确认的科目、记账时点、客户先行退款规则、权限和复核要求。 |
| SCT-Q4 | 适用检查与客户责任 | 对 EMD2、PSD2、SEPA Regulation 及其修订、Malta 规则完成专题来源审查，并关联授权、SCA、VoP、金融犯罪、数据保护与资金保护。 | 司法辖区、客户及产品事实；有权人员确认法律适用性与处理责任。 |
| SCT-Q5 | 时限、费用和客户沟通 | 补齐正常执行及异常的期限与费用来源；本轮仅整理 Recall / RFRO 部分时间条件及跟进区别。 | 产品合同、银行营业日历、时区、收到时间认定、渠道截止时间及升级安排。 |
| SCT-Q6 | 审阅、发布与使用检查 | 维护来源、说明和案例的版本关系；后续设计 SCT 正式知识链及发布检查。 | 维护者集中审阅、发布范围确认，以及独立人员或 Agent 使用反馈。 |

本轮完成条件限定为：形成可集中审阅的正文、案例回答和缺口清单，完成作者文档检查与仓库检查。维护者审阅、SCT 正式知识链、机构法律判断及真实渠道验证保持未完成，固定发布继续为 `v0.3.0`。
