# EMI Knowledge Roadmap

- 当前阶段：`v0.1 DORA`
- 当前步骤：第 3 步，建立 DORA 全景目录
- 最后更新：2026-08-31

## 阶段目标

v0.1 建立一个可以独立使用的 DORA 专家知识库最小版本。该版本需要证明三件事：

1. DORA 内容能够从权威来源逐级整理为要求、适用条件、控制、检查和证据。
2. 同一份受控内容能够同时支持人员阅读、Agent 使用和产品读取。
3. 每项知识都有明确来源、版本、状态、边界和变更记录，历史版本可以复现。

本阶段采用以下内容范围：

```text
DORA 全景目录
  +
ICT 变更管理完整知识链
```

DORA 全景目录用于建立法规、配套文件、主题和条款之间的关系。ICT 变更管理用于验证知识从来源到实施和证据的完整路径。

## v0.1 范围

### 包含

- DORA 及相关配套法律文件的官方来源清单、版本和文件关系。
- DORA 主要主题、章节和适用范围的全景目录。
- ICT 变更管理相关条款的结构化要求和待确认事项。
- 与监管要求关联的治理措施、技术控制、检查清单、测试和证据模板。
- 最小知识模型、Schema、引用规则、状态规则和版本规则。
- 面向人员的 Markdown 和面向机器的结构化发布文件。
- 独立于 EMI Harness 和其他目标产品的验证与使用示例。

### 暂不包含

- DORA 全部条款的逐条深度建模。
- 对任何具体 EMI 机构作出完整适用性或合规结论。
- MFSA 往来文件、内部制度、牌照材料和其他私有知识。
- GDPR、AML/CFT、制裁、EMD2 和其他领域的详细知识内容。
- 搜索服务、向量数据库、RAG 服务和图数据库。
- 自动抓取后直接发布、Agent 自动批准或自动覆盖历史版本。
- EMI Harness、Agent Runtime 或具体产品的接入适配器。

## 首条知识链

ICT 变更管理的首批来源基线为：

1. [Regulation (EU) 2022/2554，DORA](https://eur-lex.europa.eu/legal-content/EN/TXT/?uri=CELEX:32022R2554)，重点包括 Article 2 和 Article 9(4)(e)。
2. [Commission Delegated Regulation (EU) 2024/1774](https://eur-lex.europa.eu/eli/reg_del/2024/1774)，重点包括 Article 17 以及与治理、ICT 项目和风险管理相关的条款。
3. [MFSA：ICT Change Management under DORA](https://www.mfsa.mt/publication/ict-change-management-under-the-digital-operational-resilience-act-dora/)，作为 Malta 主管机关的说明材料单独标明来源层级。

这些来源只构成起点。第 2 步需要核对当前有效文本、修订和勘误、法律效力、适用日期、相关配套文件及来源之间的引用关系，然后才能封存来源基线。

## 来源层级

| 层级 | 内容 | 使用规则 |
| --- | --- | --- |
| **欧盟法律文件** | DORA、Delegated Regulations、Implementing Regulations、修订和勘误。 | 记录 Official Journal 或 EUR-Lex 标识、精确版本和条款位置，作为监管要求的主要依据。 |
| **欧盟监管材料** | ESAs、EBA、EIOPA、ESMA 发布的正式指引、问答和说明。 | 明确文件类型和法律地位，不能与具有约束力的法律文件混写。 |
| **成员国主管机关材料** | MFSA 等主管机关发布的规则、通告、说明和公开监管材料。 | 记录司法辖区和适用主体，区分规则、监管预期和说明性内容。 |
| **标准与辅助资料** | 国际标准、技术标准、公开研究和行业资料。 | 用于补充控制设计和理解背景，不能单独支持关键监管结论。 |
| **机构私有资料** | 内部政策、风险决定、监管往来和机构事实。 | 保存在独立私有知识层，不进入本公共仓库。 |

### 第 1 步：确认阶段范围

已确认 EMI Knowledge 作为独立专家知识库建设。v0.1 聚焦 DORA，并以 ICT 变更管理作为第一条完整知识链。EMI Harness 只保留为后续使用方，不参与核心模型和当前验收。

完成条件：

- README 说明定位、边界、治理和 DORA 当前重点。
- Roadmap 说明 v0.1 范围、步骤、交付物和完成条件。
- 公共知识、私有知识和具体机构判断的边界清楚。

### 第 2 步：建立权威来源基线

逐份核对 DORA 及 ICT 变更管理相关官方文件，建立可审查的来源记录和文件关系。

完成记录（2026-08-31）：

- 已形成并完成人工复核的 [DORA 权威来源基线](../docs/sources/dora-source-baseline.md)。
- 已核对 DORA、Directive (EU) 2022/2556、12 项二级法规、2 项 ESA 联合指引，以及 Malta 约束性文件和 MFSA 公开材料。
- 已固定英文工作版本，并区分需要合并的英文勘误和只影响其他语言的勘误。
- 已记录 ICT 变更管理的首条来源链，以及 Malta FIR/01 已被后续规则替代的版本变化。
- 仓库维护者已确认来源标识、日期、分类、链接和文件关系；Malta 具体条款映射进入第 3 步处理。

第 3 步新识别的 FIR/03 与 `EBA/GL/2025/02` 已于 2026-08-31 完成人工复核，并入来源基线 `DORA-SOURCES-2026-08-31-R2`。前序基线继续保留在 Git 历史中。

完成条件：

- 每份来源记录发布机构、文件类型、官方标识、标题、版本或日期、有效状态、适用日期、原始链接和获取日期。
- 修订、勘误、合并文本、授权依据和被引用条款之间的关系可追溯。
- 具有约束力的法律文件、监管材料和说明材料采用不同分类。
- 来源清单经过人工复核，失效链接、重复记录和版本冲突得到处理。
- 本步只确认来源事实，不提前形成机构适用性或工程控制结论。

### 第 3 步：建立 DORA 全景目录

按照 DORA 的正式结构整理主题、章节、条款和配套文件，记录 v0.1 已覆盖内容与后续缺口。

当前进展（2026-08-31）：

- 已形成 [DORA 全景目录草案](../docs/dora/dora-landscape.md)。
- 已覆盖 9 个 Chapter、Articles 1-64、12 项二级法规和 2 项 ESA 联合指引的主题位置。
- 已区分未获 EMD2 Article 9(1) 豁免与已获该豁免 EMI 的 ICT 风险管理和变更管理路径。
- 已定位 ICT 变更管理的直接条款、上下游主题，以及 Malta S.L. 330.20、Cap. 376 和 FIR/01 的相关位置。
- 已核对 amended EBA/GL/2019/04 的正式编号 `EBA/GL/2025/02`、适用日期、适用对象和修订范围，并与当前 FIR/03 一同并入已确认来源基线 R2。
- 已对照官方文本复核 9 个 Chapter、64 个 Article、12 项二级法规、监管指引、EMI 适用分支、ICT 变更管理路径和 Malta 国内层。
- 已收紧紧急变更实施后处理及运行日志的目录表述，复核方法和结论记录在全景目录第 9 节。
- 剩余工作是最终人工确认目录边界、EMI 两条路径、Malta 范围和覆盖缺口；完成后再进入第 4 步。

完成条件：

- 目录覆盖 ICT 风险管理、事件、韧性测试、ICT 第三方风险和信息共享等主要领域。
- 每个主题能够定位到 DORA 条款及已识别的配套文件。
- 适用主体、比例原则、简化框架和例外只记录来源支持的边界，未确认部分保持显式状态。
- ICT 变更管理的上下游主题和相关条款已经识别。
- 目录不包含未经来源支持的合规结论。

### 第 4 步：确认知识模型与 Schema

使用已经核对的 DORA 来源和 ICT 变更管理样例设计最小模型。模型至少需要表达来源、条款、监管要求、适用范围、人工决定、控制、规则、检查和证据之间的关系。

完成条件：

- 每类内容具有稳定标识、明确职责和允许的引用关系。
- 来源事实、解释、工程推导、待确认事项和已确认决定能够区分。
- 发布状态、确认状态、有效时间和适用范围分别表达。
- Schema 能拒绝缺少来源、重复标识、无效引用、未知状态和不完整适用范围。
- 至少使用三条真实 ICT 变更管理要求验证模型，没有为目录完整而创建空内容类型。
- 关键取舍通过设计决定记录。

### 第 5 步：建立 ICT 变更管理知识链

将已确认来源整理为可以阅读、检查和执行的知识内容。监管要求与工程控制之间的转换需要保留推导依据和人工确认边界。

完成条件：

- 相关条款已经拆分为可独立引用的监管要求。
- 每项要求记录适用条件、排除条件、来源引用和确认状态。
- 每项纳入范围的要求至少关联一个控制目标、实施规则、检查方式和证据要求。
- 常规变更、紧急变更、职责分离、安全评估、测试、批准、回退、实施后复核和记录保留等内容得到覆盖。
- MFSA 说明材料与欧盟法律文件分层引用，不扩大其法律效力。
- 无法由公开来源确认的机构决定和实施参数保持待确认。

### 第 6 步：实现校验与生成

使用 TypeScript 实现确定性校验和发布生成流程。工具只处理仓库中的受控文件，不从网络自动修改正式内容。

完成条件：

- 一个命令可以执行格式、Schema、引用、唯一性、状态和必要字段检查。
- 自动化测试覆盖有效内容和主要失败场景。
- 人员文档和机器文件来自同一份受控内容，或者通过双向一致性检查保持同步。
- 生成结果可重复，相同输入产生相同内容摘要。
- 校验失败会阻止发布，不允许静默跳过未知字段或断裂引用。

### 第 7 步：发布 v0.1

将通过校验和审查的内容封存为固定版本，同时保留覆盖范围和限制说明。

完成条件：

- 发布结果包含版本、内容摘要、来源基线、生成工具版本、覆盖范围和已知限制。
- 人员文档可以从要求导航到来源、控制、检查和证据。
- 机器文件通过公开 Schema 校验，并能按稳定标识解析关系。
- 所有待确认事项在发布结果中可见。
- 人工审查记录绑定准确版本；缺少所需审查时只能发布相应级别的工程或来源基线。
- Git tag 和发布记录能够复现全部内容。

### 第 8 步：独立使用验收

在不接入 EMI Harness 的情况下验证三个使用场景。

完成条件：

- 人员可以从一个 ICT 变更场景找到适用要求、来源、控制、检查和证据。
- Agent 只加载指定版本后，能够引用稳定标识回答问题，并保留待确认事项和来源层级。
- 示例产品能够读取机器文件，完成来源到要求、要求到控制以及控制到证据的查询。
- 三类使用方得到的核心事实、版本和状态一致。
- 验收记录说明发现的问题、修正版本和剩余限制。

## v0.1 发布边界

v0.1 的公开内容可以达到来源基线或工程基线。发布级别取决于实际完成的人工审查。任何缺少授权确认的法律适用性、机构决定或风险接受都保持待确认状态。

v0.1 完成只说明知识链、治理和发布方法已经通过首个 DORA 主题验证。它不代表任何机构已经满足 DORA，也不构成法律意见、监管批准或生产控制认证。

## 后续方向

v0.1 完成后，根据实际使用结果选择下一个 DORA 主题。候选方向包括 ICT 事件管理与报告、业务连续性与恢复测试、ICT 第三方风险或 ICT 风险管理框架。具体顺序通过新的阶段计划确认。

EMD2、GDPR、AML/CFT 和制裁知识在 DORA 方法稳定后逐步进入独立阶段，每个领域都从一条可验证的完整知识链开始。

## 维护规则

- 每个步骤开始、完成或停止时更新状态和实际结果。
- 每次只推进一个能够独立检查的最小交付物。
- 范围、知识模型或发布规则变化时，先更新 README、Roadmap 或设计决定。
- 发现来源变化时创建待审查更新，已经发布的历史版本保持不变。
- 能由 Schema、测试或脚本判断的规则进入自动检查。
- 每个完整步骤单独提交并推送，提交信息说明改动和原因。
